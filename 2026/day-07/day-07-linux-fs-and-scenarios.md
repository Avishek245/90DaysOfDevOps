# Day 07 - Linux File System Hierarchy & Scenario Practice

## Part 1: Linux File System Hierarchy

### / (root)
- Contains the top-level directories of the entire Linux filesystem.
- Example contents: `bin`, `etc`, `home`, `var`
- I would use this when I need to start navigating the filesystem and locate other important directories.

### /home
- Contains personal user directories.
- Example contents: `user1`, `user2`, `.bashrc`
- I would use this when accessing user files, documents, or user-specific settings.

### /root
- Home directory for the root user.
- Example contents: `.bashrc`, `admin-scripts`, `root-only-files`
- I would use this when performing administrative tasks as the root user.

### /etc
- Stores system-wide configuration files.
- Example contents: `passwd`, `hostname`, `ssh/`
- I would use this when changing system settings or configuring services.

### /var/log
- Holds log files generated by the system and applications.
- Example contents: `syslog`, `auth.log`, `dmesg`
- I would use this when troubleshooting issues or checking system events.

### /tmp
- Used for temporary files created by applications and processes.
- Example contents: `temp1234`, `session.sock`, `cache/`
- I would use this when needing a place for short-lived files that do not need to persist.

### /bin
- Contains essential user command binaries needed for basic system operation.
- Example contents: `ls`, `cp`, `bash`
- I would use this when executing core commands available on the system.

### /usr/bin
- Contains non-essential user command binaries and utilities.
- Example contents: `python3`, `git`, `nano`
- I would use this when running tools that are not required for minimal system boot.

### /opt
- Used for optional or third-party software installations.
- Example contents: `google`, `vscode`, `myapp`
- I would use this when installing or managing optional applications outside the standard package system.

## Part 2: Scenario-Based Practice

### Scenario 1: Service Not Starting

Step 1: `systemctl status myapp`
Why: To verify whether the service is active, failed, or not found.

Step 2: `journalctl -u myapp -n 50`
Why: To inspect the most recent logs for errors and failure details.

Step 3: `systemctl is-enabled myapp`
Why: To confirm whether the service is configured to start automatically on boot.

Step 4: `systemctl restart myapp`
Why: To attempt restarting the service after identifying the issue.

### Scenario 2: High CPU Usage

Step 1: `top`
Why: To view live CPU usage and identify the top consuming processes.

Step 2: `ps aux --sort=-%cpu | head -10`
Why: To list the highest CPU processes in a sorted snapshot.

Step 3: `pidstat -p <PID> 1 5`
Why: To monitor the specific process CPU usage over time and confirm it is the cause.

### Scenario 3: Finding Service Logs

Step 1: `systemctl status docker`
Why: To verify whether the docker service is running and check its current status.

Step 2: `journalctl -u docker -n 50`
Why: To view the last 50 lines of docker service logs for recent events.

Step 3: `journalctl -u docker -f`
Why: To follow logs in real time while reproducing or observing ongoing issues.

### Scenario 4: File Permissions Issue

Step 1: `ls -l /home/user/backup.sh`
Why: To check the current file permissions and identify whether execute permission is missing.

Step 2: `chmod +x /home/user/backup.sh`
Why: To add execute permission so the script can be run.

Step 3: `./backup.sh`
Why: To verify the script now runs successfully after permission changes.
